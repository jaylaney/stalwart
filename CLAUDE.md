# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is a fork of the Stalwart mail server (Rust, edition 2024, Cargo workspace, base 1.0.3: upstream tag `v1.0.3`, commit `8b32686532d34623e9ce8e1237cf2bed9554af38`). The fork's own version is separate from the upstream base: `fork-release.toml` holds both (fork `0.4.0-beta.1` on upstream `v1.0.3`), the shipping `stalwart` package carries the fork version, and the internal crates keep upstream's `1.0.3` (the fork-owned `vault` crate keeps `0.16.25`). Jay is building a zero-access (encrypted-at-rest) calendar product on branch `zero-access`. Read `docs/README-dev.md` for developer notes and `docs/superpowers/plans/2026-10-06-zero-access-plan1-outcome.md` before touching fork code. The fork moved from 0.16.27 through 1.0.1 to 1.0.3 on fresh stores; the upgrade's outcome note (`docs/superpowers/plans/2026-10-27-stalwart-1-upgrade-outcome.md`) gives, in its hook inventory, interface sheet and deleted-paths table, the 1.0 site of every 0.16 path that moved. A path below that names a 0.16 site is called out as such.

## Commands

Every shell command that uses cargo must start with `export PATH="/opt/homebrew/opt/rustup/bin:$PATH"` (Homebrew's keg-only rustup; Claude Code's shell is non-interactive, so the zshrc PATH does not apply).

- Product build (shipping configuration, never the `enterprise` feature): `cargo build --release -p stalwart --no-default-features --features rocks`. Add other store backends by name (`sqlite`, `postgres`, `mysql`, ...). For a local manual-test binary, prefix the same command with `CARGO_PROFILE_RELEASE_LTO=thin CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16`: the release profile's fat LTO and single codegen unit end in a long single-threaded tail, which this parallelises; the binary is slightly larger and slower, and switching between the two settings rebuilds from scratch. `-p http` is ambiguous in this workspace (the dependency graph also holds the crates.io `http` 1.x crate, through hyper, reqwest, axum, h2, tonic and others); use `-p http@1.0.3`. The shipping binary's `--version` prints `Stalwart Server fork v<fork version> (upstream v1.0.3 <commit>; source <commit>; clean|dirty)`; `scripts/release/verify_product.py` checks it, and `.github/workflows/product-build.yml` builds the Linux release artifact (its dispatch needs Jay's authorization).
- Stores: 1.0.3 cannot open a 0.16 store, and the fork has no conversion. `Server::verify_schema_version` (`common/src/manager/schema.rs`, called from `main` after boot) writes the schema version on a new store (base 7, with `DATABASE_SCHEMA_OSS_FLAG` set by a build without `enterprise`) and refuses any other value: a 0.16 store, a store of the other edition, or a newer one. Every install, test server and local run starts on a fresh store; there is no in-place migration (upstream removed the `migration` crate).
- Unit tests: `cargo test -p vault`, `cargo test -p common`, `cargo test -p http@1.0.3 --lib --bins --features test_mode,enterprise` (the http crate's `za_test` tests), `cargo test -p smtp --lib --bins --features test_mode` (including the DKIM tests that compile only without `enterprise`). `cargo test -p common --lib` compiles on its own at 1.0; CI's workspace step runs every crate's unit tests with the features in `UNIT_TEST_FEATURES` (below).
- Integration tests live in the `tests` crate and need `STORE=RocksDb RUST_MIN_STACK=16777216`. Each suite is ONE test function that runs its sub-modules in order against one server; you select the suite by filter and cannot select a sub-module:

  - `cargo test -p tests za::cache_swap::cache_swap_tests -- --exact --nocapture`: a suite of its own, new at 1.0 (`tests/src/za/cache_swap.rs`). Its server enables 1.0's cache swap tier (`TestServerBuilder`'s swap option, `min_account_size` 0, a small `flush_changes`, upgrade ruling 20) and checks that snapshots are built from stored rows only and that keys, tokens and the authentication generation are never swapped. Run it alone (default ports) and without `BLOB_STORE`: 1.0.3 refuses a filesystem blob store for the swap tier (ruling 68).
  - `webdav_tests`: upstream CalDAV/CardDAV suite. `ZA_KEY_ACCOUNTS=1` runs it with every user provisioned as a key account.
  - `imap_tests` and `jmap_tests` honour `ZA_KEY_ACCOUNTS=1` too (mail spec 11): their users become key accounts (the admin and the groups stay plain), the affected sub-modules use the variants in `tests/src/imap/za_variants.rs` (fetch, store, acl, antispam) and `tests/src/jmap/za_variants.rs` (query, search_snippet, query_changes, copy, thread_get, thread_merge, acl, push_subscription, blob, file_node, the calendar refusals, principal_get), and JMAP's `compliance` sub-test is skipped with a printed note. IMAP `search` and `thread` run upstream's bodies in both modes. JMAP's `query`, `search_snippet`, `query_changes`, `thread_get` and `thread_merge` variants assert upstream's outcomes and exercise the keyed request path. Query, snippet and the key accounts in thread merge explicitly wait for the sealed index with `za_index_current`.
  - Others: `system_tests`, `imap_tests`, `jmap_tests`, etc. There is no `smtp_tests` suite: the SMTP tests are individual functions that CI runs with `cargo test -p tests smtp`. `system_tests` uses bounded authentication-expiry checks, restores temporary upload limits before later imports, and controls its task-deadline fixture; `directory_tests` needs Docker (OpenLDAP, and Keycloak pinned to `26.8.1`), and `automation_tests` needs Docker too (Pebble, challtestsrv, PowerDNS). CI reruns each CalDAV step once, and the plain-mode `jmap_tests` step once (for upstream's timing-flaky `calendar::notification` sub-test).

After a change to `tests/Cargo.toml`, compare `cargo test --workspace --lib --bins -- --list` (less the `tests`, `scim` and `scim-proto` binaries) with the step's `-- --list`.

## Repository rules (AGENTS.md, CONTRIBUTING.md)

- Never open GitHub issues, pull requests or security reports against upstream `stalwartlabs/stalwart`, and do not draft them for the user. `origin` is Jay's fork (`jaylaney/stalwart`) and the only remote, on purpose: there is no `upstream` remote, and `gh` is set to default to the fork (`gh repo set-default jaylaney/stalwart`); still pass `--repo jaylaney/stalwart` to every `gh` command that writes. To merge an upstream release, fetch its tag by URL (`git fetch https://github.com/stalwartlabs/stalwart.git tag v1.0.1 --no-tags`) into a branch, add the tag and its commit to `PINNED_UPSTREAM_TAGS` in `scripts/release/verify_product.py` (the verifier refuses an upstream pin when a later known release is in the source's history, or when the tag's version differs from the internal crates' package version in `crates/common/Cargo.toml`), and follow README-dev's "Merging upstream"; never push to upstream. Upstream bugs and questions go to support.stalw.art, by the human. Do not request CVEs or advisories.
- Upstream bugs observed during fork work are recorded in Jay's private tracker `jaylaney/stalwart-issues` (labels `bug`, `confidence: high|medium|low`, `mitigated in fork`, `needs decision`; each entry gives the code location at the fork's base version, the effect, a repro sketch, how it was established, the fork's status and a suggested fix), never in this repository's public tracker, its committed docs or upstream; the spec and outcome notes describe a fork-side mitigation or an accepted inherited behaviour without naming the tracker. Before filing one, search upstream's issue list (`gh issue list --repo stalwartlabs/stalwart --state all --search "<terms>"`, read-only) and reference any existing upstream issue in the entry instead of describing the bug as new.
- Upstream does not accept AI-generated code or pull requests from non-vouched contributors. This fork publishes under AGPL-3.0 and does not contribute back.
- Code under `cfg(feature = "enterprise")` and the whole `scim` crate are licensed only under the Stalwart Enterprise License and are excluded from the product build. The `tests` crate enables `enterprise` on `store`, `directory`, `coordinator` (and others) for upstream's own tests; leave that.

## Architecture

Crates (under `crates/`):
- `main`: the `stalwart` binary; `types`: shared ids and `PrincipalField`; `utils`: helpers and proc macros.
- `common`: the shared core (`Server`, `Inner`, `Core`, `Data`, `Caches`), config parsing, boot, authentication routing, cache invalidation.
- `store`: storage backends and `RegistryStore`; `registry`: registry object schema (generated) and pickling; `directory`: internal/external directories and `Credentials`; `coordinator`: cluster pub/sub.
- `http` (+ `http-proto`): hyper listener, routing, `/api/*` management API, auth layer; `jmap` (+ `jmap-proto`): JMAP and the registry mapping layer; `dav` (+ `dav-proto`): CalDAV/CardDAV/WebDAV handlers; `groupware`: calendar/contact/file resources, iTIP scheduling.
- `email`, `imap` (+ `imap-proto`), `pop3`, `managesieve`, `smtp` (+ `smtp-proto`, `smtp-report`), `spam-filter`, `nlp`, `sieve`: mail stack. `services`: background tasks (`task_manager`, with the task bodies in `task_manager/tasks/`), the index queue (`index_queue`, new at 1.0) and the broadcast subscriber. `trc`: tracing events and metrics; `telemetry`: the exporters and stored traces (moved out of `common` at 1.0).
- Vendored into the workspace at 1.0, so their changes now arrive with upstream merges: `calcard` (iCalendar and vCard; sealed bundles embed its rkyv layout), `smtp-proto`, `sieve`, `jmap-tools`; also `s3` and `text-extract`. 0.16's `migration` crate is gone: 1.0 does not migrate stores in place.

Startup: `main` calls `BootManager::init` (`common/src/manager/boot.rs`): config JSON path (`--config` or `CONFIG_PATH`) -> `RegistryStore::init` -> `Bootstrap` (inserts safe defaults) -> `Listeners` -> `Storage`/`Telemetry` -> `Core`, `Data`, `Caches` -> `Arc<Inner>`. `Server` is a cheap per-use view built with `inner.build_server()`. Then `verify_schema_version` (refuses a store of another schema version or edition), `start_services`, `start_queue_manager`, and `init.servers.spawn` starts one session manager per listener protocol (SMTP/LMTP, HTTP, IMAP, POP3, ManageSieve), plus the broadcast subscriber.

HTTP request flow: `crates/http/src/request.rs` routes on the first path segment: `/jmap`, `/dav`, `/.well-known`, `/auth` (OAuth), `/api`, `/scim`, `/form`, etc. Each arm authenticates itself via `Authenticator::authenticate_headers` (`http/src/auth/authenticate.rs`; upstream's auth cache, `HttpAuthEntries` in `common/src/cache/http_auth.rs`, with its revocation epoch, and the fork's resident-key lookup) -> `Server::authenticate` -> `common::auth::authentication::route_auth_request` (shared by every protocol, including IMAP/POP3/SMTP/ManageSieve) -> `AccessToken`. Handlers then call `jmap`/`dav`/`groupware`/`email` -> `store`. `crates/http/src/api/mod.rs` dispatches `/api/*` (`auth`, `account`, `token`, `discover`, `schema`, `vault`, `shares`, ...).

Registry: configuration and accounts are registry objects. The Rust types in `crates/registry/src/schema/*` and the event enums in `crates/trc/src/event/enums.rs` are GENERATED by a tool that is not in this repo ("auto-generated, do not edit"). Do not hand-edit them and do not add settings, permissions or event variants; the fork uses environment variables instead (`ZA_KEY_IDLE_SECS`, `ZA_KEY_MAX_AGE_SECS`, `ZA_KEY_MAX_ENTRIES`, `ZA_ACCOUNT_PAGE_ORIGIN`, `ZA_UID_LEASE_SECS`). Release 7 adds
`ZA_SEARCH_MEM_MB`, `ZA_SEARCH_THREAD_MEM_MB`, `ZA_SEARCH_ACCOUNT_MAX_MB`,
`ZA_SEARCH_IDLE_SECS`, `ZA_SEARCH_PASS_CAP`, `ZA_SEARCH_PASS_MB`,
`ZA_SEARCH_PASS_HIDDEN_KB`, `ZA_SEARCH_PASS_MS`, `ZA_SEARCH_WAIT_SECS`,
`ZA_SEARCH_SEGMENTS`, `ZA_SEARCH_CHECKPOINT`, `ZA_SEARCH_SKIP_AFTER`,
`ZA_SEARCH_ABSENT_RETRY_SECS` and `ZA_SEARCH_PAD_MIN`.
[Searching key accounts](docs/README-dev.md#searching-key-accounts) has the defaults,
the four startup refusals and the cluster-wide account-cap rule. Registry objects are edited through JMAP `x:<Type>/set` calls (see `tests/src/utils/registry.rs`).

Storage: `store` abstracts RocksDB, SQLite, FoundationDB, PostgreSQL and MySQL. Stored structs are rkyv archives read with unchecked zero-copy access (`rkyv::access_unchecked` in `store/src/write/serialize.rs`), so stored struct layouts must never change. Conditional writes use `AssertValue` (`store/src/write/assert.rs`). Per-account Principal properties are keyed by `PrincipalField` (`types/src/field.rs`). At 1.0 the server compresses its archives with zstd (most against the dictionaries in `resources/zstd/`) and RocksDB compresses most column families' blocks with LZ4, so a byte search of the store finds nothing unless it decodes them (`scripts/local-server/leakcheck.sh` does). 1.0's object-metadata containers (`Collection::Metadata`, `types/src/metadata/`) replace 0.16's `types::DeadProperty` (`types/src/dead_property.rs`): DAV dead properties, IMAP annotations and JMAP metadata all live there.

Caches (`common::Caches`): account and access-token caches, `http_auth` (upstream's `HttpAuthEntries`, keyed by a per-process SipHash of the token; its `HttpAuthCache` entry has no fork field at 1.0: upgrade ruling 10 re-derives R35's impersonation marker on a cache hit), the zero-access key cache `za_keys` (keyed by a keyed BLAKE3 fingerprint of the token, `Caches::za_fingerprint`), DAV resource caches, and 1.0's cache swap tier (`common/src/cache/swap/`, exercised by `cache_swap_tests`). `CacheInvalidation` (`common/src/ipc.rs`) is broadcast across cluster nodes. Cache loaders are fenced by `Caches::account_epoch`.

Test harness: `TestServer`/`TestServerBuilder` (`tests/src/utils/server.rs`), one server per suite on port 8899 with self-signed TLS. `Account` helpers in `tests/src/utils/account.rs` (`create_key_user_account` makes a zero-access account); fork helpers in `tests/src/utils/za.rs`. `assert_is_empty` scans every store subspace (`tests/src/utils/cleanup.rs`); upstream's `webdav_tests` sub-modules call it at their end, while the za suite calls it once, at the very end (`tests/src/za/mod.rs`) after destroying its key accounts, so za sub-modules must delete what they create. Vault, pin and search manifest records (fields 150–152) and principal-linked search blobs are exempted there only while their account still exists. The za suite skips every account's drain after setup (`test_hooks::set_drain_skip(DRAIN_SKIP_ALL)`), so modules that read pending items at store level keep working; the drain modules (`tests/src/za/drain.rs`, `drain_limits.rs`, `pinning.rs`, `leak::test_drain`, `leak::test_pins`) turn it on with the `DrainOn` guard. Invariants (spec section 12):
- No stored struct changes layout; ciphertext rides in existing fields.
- The vault record is the sole authority for login. Every write is conditional on its revision (the authentication generation), verification reads it once, and no registry-only edit may change login outcome.
- Key material lives in `Zeroizing` buffers with a silent `Debug`, only in process memory, and never in logs, traces or errors. No cache retains a credential or a reversible form of one.
- Non-key accounts take unchanged upstream code paths.
- `Server::authenticate` returns keyless tokens on every protocol. `SessionKeys` are attached by the HTTP layer for one request, and by the IMAP and POP3 login handlers for the life of the authenticated connection (mail spec 3.3); WebSocket, EventSource, ManageSieve and SMTP sessions never hold them. Background code never needs a key; if a path would, gate it.
- Sealing never adds, removes or reorders iCalendar components; visibility is an allowlist; the index builder only sees the stored sealed archive. Field policy 2 (calendar spec revision 8): `CLASS` is visible on VEVENT, VTODO and VJOURNAL when its one value is standard (PUBLIC, PRIVATE or CONFIDENTIAL); any other value, a second value or another component keeps it sealed, and an extension parameter on it is sealed (`seal::policy::is_visible_entry`). Upstream's `refresh_from_content` then derives `EVENT_PRIVATE` and `EVENT_SECRET` from the stored tree; no fork code computes them. The operator therefore learns each event's classification. `POLICY_VERSION` stays 1: field policy 2 is a property of the store (a 1.0 store starts fresh), so a later allowlist change on a store holding data would need a per-object marker.
- Keep the fork diff narrow: new modules plus one-line call insertions at existing sites. Merge hotspots with upstream are `http/src/auth/authenticate.rs` and `common/src/auth/authentication.rs`.
- Mail-protocol traces never carry a login credential (issue #20, calendar spec section 10): before authentication, IMAP, POP3 and ManageSieve trace raw input and output as `[redacted]` and redact only the errors that can quote input (imap-proto's BAD errors; POP3 parse errors marked BAD when queued pre-auth); SMTP masks SASL-state reads, reads holding `AUTH` plus whitespace anywhere (joined to the partial request line) and reads up to the line end after a 334 (`SessionData::za_answers_334`); OAuth form bodies are read untraced. This applies to every account, since the account is unknown before authentication. After authentication the rule is whole-session for key accounts (mail spec 10, issue #21): IMAP and POP3 trace a key account's session as `[redacted]` throughout (raw input and output, BAD errors, the details of `ImapEvent::Fetch` and `Store`); SMTP redacts every read of a transaction submitted by a key account (`SessionData::za_key_sender()`) or delivering to one (`SessionData::za_key_rcpt`, set at RCPT by `Session::za_has_key_rcpt` through `Server::za_is_key_rcpt` (`crates/smtp/src/inbound/rcpt.rs`) and noted again at the end of DATA for recipients a milter, hook or script added (`crates/smtp/src/inbound/data.rs`), so a read holding an RCPT and a DATA or BDAT command is redacted for every account, plan 13 ruling R41) and that transaction's milter and spam-filter events (`MilterClient::redact`, `SpamFilterInput::za_redact`); a key account's own Sieve runtime-error reason at delivery (`crates/email/src/sieve/ingest.rs`) is redacted and its `MessageIngest` events carry `[redacted]` instead of the Message-ID; the vacation compile error reason names its position only (`compile error at line N, column M`) for every account.
