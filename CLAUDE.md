# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is a fork of the Stalwart mail server (Rust, edition 2024, Cargo workspace, base 0.16.26). Jay is building a zero-access (encrypted-at-rest) calendar product on branch `zero-access`. Read `docs/superpowers/plans/README-dev.md` for developer notes and `docs/superpowers/plans/2026-10-06-zero-access-plan1-outcome.md` before touching fork code.

## Commands

Every shell command that uses cargo must start with `export PATH="/opt/homebrew/opt/rustup/bin:$PATH"` (Homebrew's keg-only rustup; Claude Code's shell is non-interactive, so the zshrc PATH does not apply).

- Product build (shipping configuration, never the `enterprise` feature): `cargo build --release -p stalwart --no-default-features --features rocks`. Add other store backends by name (`sqlite`, `postgres`, `mysql`, ...). For a local manual-test binary, prefix the same command with `CARGO_PROFILE_RELEASE_LTO=thin CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16`: the release profile's fat LTO and single codegen unit end in a long single-threaded tail, which this parallelises; the binary is slightly larger and slower, and switching between the two settings rebuilds from scratch. `-p http` is ambiguous in this workspace; use `-p http@0.16.26`.
- Unit tests: `cargo test -p vault`, `cargo test -p common`, `cargo test -p http@0.16.26 --features test_mode`. `cargo test -p common --features test_mode` without `enterprise` fails to compile upstream (telemetry test data); the `tests` crate enables both.
- Integration tests live in the `tests` crate and need `STORE=RocksDb RUST_MIN_STACK=16777216`. Each suite is ONE test function that runs its sub-modules in order against one server; you select the suite by filter and cannot select a sub-module:
  - `cargo test -p tests za_tests -- --nocapture`: zero-access account API, caches, CORS, registry refusals.
  - `webdav_tests`: upstream CalDAV/CardDAV suite. `ZA_KEY_ACCOUNTS=1` runs it with every user provisioned as a key account.
  - `imap_tests` and `jmap_tests` honour `ZA_KEY_ACCOUNTS=1` too (mail spec 11): their users become key accounts (the admin and the groups stay plain), the sub-modules that search, sort, copy across accounts, share or train run the variants in `tests/src/imap/za_variants.rs` (search, fetch, store, thread, acl, antispam) and `tests/src/jmap/za_variants.rs` (query, search_snippet, query_changes, copy, thread_get, thread_merge, acl, push_subscription, blob, file_node, the calendar refusals, principal_get), and JMAP's `compliance` sub-test is skipped with a printed note.
  - Others: `system_tests`, `imap_tests`, `jmap_tests`, etc. There is no `smtp_tests` suite: the SMTP tests are individual functions that CI runs with `cargo test -p tests smtp`. `system_tests` is timing-flaky locally (OIDC, quota and antispam sub-tests fail one at a time); `directory_tests` needs a Docker OpenLDAP container.
  - Upstream's `cal_itip` sub-test of `webdav_tests` is timing-flaky (DTSTAMP index mismatch, `tests/src/webdav/cal_itip.rs`); rerun once before treating a failure there as a regression. CI reruns each CalDAV step once, and the plain-mode `jmap_tests` step once (for upstream's timing-flaky `calendar::notification` sub-test).
  - Upstream's `calendar::notification` sub-test of `jmap_tests` is timing-flaky (the 200 ms wait at `tests/src/jmap/calendar/notification.rs:184` before the assertion at `:191`); rerun once before treating a failure there as a regression. Key-mode `jmap_tests` does not run it (JMAP calendars answer `accountNotSupportedByMethod` for key accounts).
  - Four upstream SMTP tests (`dkim2_dsn_is_signed`, `lmtp_delivery`, `queue_retry`, `manage_reports`) are timing-flaky when the whole `smtp` filter runs in parallel; rerun the failures by name.
- rustfmt: `cargo fmt -p <crate> -- --check`; for the http crate cargo rejects `-p http@0.16.26` for fmt, so use `cargo fmt --manifest-path crates/http/Cargo.toml -- --check`. Workspace lints are strict; build output must stay warning-free for new code.
- Local manual run: tracked scripts in `scripts/local-server/` (its `README.md` has the first-run steps; `env.sh` holds the shared settings), with per-machine state (data store, `local.env`, `tls/`, logs) in the git-ignored `.run/` by default (`ZA_RUN_DIR` overrides). First boot is `start-recovery.sh` then `provision.sh`; afterwards `start.sh`. `--config` takes a JSON data-store file (`{"@type":"RocksDb","path":...}`); a missing file means web bootstrap mode. `STALWART_RECOVERY_ADMIN=user:pass` sets a fallback admin.

## Architecture

Crates (under `crates/`):
- `main`: the `stalwart` binary; `types`: shared ids and `PrincipalField`; `utils`: helpers and proc macros.
- `common`: the shared core (`Server`, `Inner`, `Core`, `Data`, `Caches`), config parsing, boot, authentication routing, cache invalidation.
- `store`: storage backends and `RegistryStore`; `registry`: registry object schema (generated) and pickling; `directory`: internal/external directories and `Credentials`; `coordinator`: cluster pub/sub.
- `http` (+ `http-proto`): hyper listener, routing, `/api/*` management API, auth layer; `jmap` (+ `jmap-proto`): JMAP and the registry mapping layer; `dav` (+ `dav-proto`): CalDAV/CardDAV/WebDAV handlers; `groupware`: calendar/contact/file resources, iTIP scheduling.
- `email`, `imap` (+ `imap-proto`), `pop3`, `managesieve`, `smtp`, `spam-filter`, `nlp`: mail stack. `services`: background tasks and broadcast subscriber. `migration`: data migrations (run before services start). `trc`: tracing events and metrics.

Startup: `main` calls `BootManager::init` (`common/src/manager/boot.rs`): config JSON path (`--config` or `CONFIG_PATH`) -> `RegistryStore::init` -> `Bootstrap` (inserts safe defaults) -> `Listeners` -> `Storage`/`Telemetry` -> `Core`, `Data`, `Caches` -> `Arc<Inner>`. `Server` is a cheap per-use view built with `inner.build_server()`. Then migrate, `start_services`, `start_queue_manager`, and `init.servers.spawn` starts one session manager per listener protocol (SMTP/LMTP, HTTP, IMAP, POP3, ManageSieve), plus the broadcast subscriber.

HTTP request flow: `crates/http/src/request.rs` routes on the first path segment: `/jmap`, `/dav`, `/.well-known`, `/auth` (OAuth), `/api`, `/scim`, `/form`, etc. Each arm authenticates itself via `authenticate_headers` (`http/src/auth/authenticate.rs`, which holds the fingerprinted auth cache) -> `Server::authenticate` -> `common::auth::authentication::route_auth_request` (shared by every protocol, including IMAP/POP3/SMTP/ManageSieve) -> `AccessToken`. Handlers then call `jmap`/`dav`/`groupware`/`email` -> `store`. `crates/http/src/api/mod.rs` dispatches `/api/*` (`auth`, `account`, `token`, `discover`, `schema`, `vault`, ...).

Registry: configuration and accounts are registry objects. The Rust types in `crates/registry/src/schema/*` and the event enums in `crates/trc/src/event/enums.rs` are GENERATED by a tool that is not in this repo ("auto-generated, do not edit"). Do not hand-edit them and do not add settings, permissions or event variants; the fork uses environment variables instead (`ZA_KEY_IDLE_SECS`, `ZA_KEY_MAX_AGE_SECS`, `ZA_KEY_MAX_ENTRIES`, `ZA_ACCOUNT_PAGE_ORIGIN`, `ZA_UID_LEASE_SECS`). Registry objects are edited through JMAP `x:<Type>/set` calls (see `tests/src/utils/registry.rs`).

Storage: `store` abstracts RocksDB, SQLite, FoundationDB, PostgreSQL and MySQL. Stored structs are rkyv archives read with unchecked zero-copy access (`rkyv::access_unchecked` in `store/src/write/serialize.rs`), so stored struct layouts must never change. Conditional writes use `AssertValue` (`store/src/write/assert.rs`). Per-account Principal properties are keyed by `PrincipalField` (`types/src/field.rs`).

Caches (`common::Caches`): account and access-token caches, `http_auth`, the zero-access key cache `za_keys`, DAV resource caches. `CacheInvalidation` (`common/src/ipc.rs`) is broadcast across cluster nodes. Cache loaders are fenced by `Caches::account_epoch`.

Test harness: `TestServer`/`TestServerBuilder` (`tests/src/utils/server.rs`), one server per suite on port 8899 with self-signed TLS. `Account` helpers in `tests/src/utils/account.rs` (`create_key_user_account` makes a zero-access account); fork helpers in `tests/src/utils/za.rs`. `assert_is_empty` scans every store subspace (`tests/src/utils/cleanup.rs`); upstream's `webdav_tests` sub-modules call it at their end, while the za suite calls it once, at the very end (`tests/src/za/mod.rs`) after destroying its key accounts, so za sub-modules must delete what they create. Vault and pin records (fields 150 and 151) are exempted there only while their account still exists. The za suite skips every account's drain after setup (`test_hooks::set_drain_skip(DRAIN_SKIP_ALL)`), so modules that read pending items at store level keep working; the drain modules (`tests/src/za/drain.rs`, `drain_limits.rs`, `pinning.rs`, `leak::test_drain`, `leak::test_pins`) turn it on with the `DrainOn` guard. Test hooks: `FAN_OUT_PAUSE`, `PUT_PAUSE`, `COMMIT_PAUSE`, `COMMIT_FAIL_ONCE`, `TASK_CONSUMER_PAUSE`, `DRAIN_LOOKUP_PAUSE`, `DRAIN_LEASE_PAUSE`, `DRAIN_FAIL_ONCE`, `PRIVATE_KEY_FAIL_ONCE`, `DRAIN_ENUMERATE_FAIL_ONCE`, `DRAIN_FAIL_ITEM`, `DRAIN_READ_FAIL_ITEM`, `PIN_DECIDE_PAUSE`, `RETIRE_PAUSE`, `REDELIVER_CLEANUP_PAUSE`, `PIN_WRITE_FAIL_ONCE`, `INGEST_PAUSE`, `COPY_PAUSE`, `SETUP_TOKEN_PAUSE`, `FORCE_SQL_STORE`, the drain skip, the lease, retry and redelivery batch overrides (`crates/common/src/za/test_hooks.rs`).

## Zero-access fork

Spec: `docs/superpowers/specs/2026-10-06-zero-access-calendar-design.md` (revision 7, approved). Trust model: the operator cannot read data at rest or while the user is logged out; native CalDAV clients stay unmodified; the running server holds plaintext during a session.

Where the code lives:
- `crates/vault`: key primitives (`keys`, which also holds the display fingerprints and `WrapMark`), the vault record (`record`), the pin record (`pins`), recovery key, `SessionKeys` (`session`), the key cache (`cache`). `ZA_MARKER = "$za$"`.
- `crates/common/src/auth/vault.rs`: vault storage and verification (`PrincipalField::ZeroAccessVault = 150`; 46 is taken upstream); key pinning adds `za_vault_commit`, `za_pin_transact`, `za_self_check`, `za_served_public_key` and the pin record's field, `PrincipalField::ZeroAccessPins = 151`. `crates/common/src/auth/authentication.rs`: the marker-credential diversion inside `route_auth_request`.
- `crates/http/src/auth/authenticate.rs`: keyed-fingerprint auth cache, generation fence, test-mode pause hooks (`za_test`).
- `crates/http/src/api/vault.rs`: eight of the twelve `/api/vault/*` endpoints (`setup-token`, `setup`, `password`, `recover`, `recovery-key`, `app-password`, `app-password/revoke`, `totp`) plus CORS helpers; `crates/http/src/api/contacts.rs`: the other four, the contacts endpoints (`contacts`, `contacts/lookup`, `contacts/pin`, `contacts/forget`; key-pinning spec 6). Every vault write goes through `za_commit` or the common helper it wraps, `Server::za_vault_commit` (`crates/common/src/auth/vault.rs`, key-pinning spec 4.5), except the self-check's repair: `self_check_store` commits it through `vault_commit_store`, and `Server::za_self_check` then invalidates the account itself. Never call `za_vault_write` directly.
- `crates/jmap/src/registry/mapping/{principal,account}.rs`: refusals of registry credential edits for key accounts.
- `crates/groupware/src/calendar/drain.rs`: the drain (invitations spec 6).
- `crates/groupware/src/calendar/fanout.rs`: the fan-out, in key pinning's four phases (spec 5.2: resolve, decide and pin, deliver, retire), with `ZaFanOutKind` (`Change`, `Deletion`, `Redelivery`); `pinning.rs`: the full state, the participation REPLY and the fork DECLINED; `sequence.rs`: the SEQUENCE floor and the reconciliation.
- Tests: `tests/src/za/`, helpers in `tests/src/utils/za.rs`.

Invariants (spec section 12):
- No stored struct changes layout; ciphertext rides in existing fields.
- The vault record is the sole authority for login. Every write is conditional on its revision (the authentication generation), verification reads it once, and no registry-only edit may change login outcome.
- Key material lives in `Zeroizing` buffers with a silent `Debug`, only in process memory, and never in logs, traces or errors. No cache retains a credential or a reversible form of one.
- Non-key accounts take unchanged upstream code paths.
- `Server::authenticate` returns keyless tokens on every protocol. `SessionKeys` are attached by the HTTP layer for one request, and by the IMAP and POP3 login handlers for the life of the authenticated connection (mail spec 3.3); WebSocket, EventSource, ManageSieve and SMTP sessions never hold them. Background code never needs a key; if a path would, gate it.
- Sealing never adds, removes or reorders iCalendar components; visibility is an allowlist; the index builder only sees the stored sealed archive.
- Keep the fork diff narrow: new modules plus one-line call insertions at existing sites. Merge hotspots with upstream are `http/src/auth/authenticate.rs` and `common/src/auth/authentication.rs`.
- Mail-protocol traces never carry a login credential (issue #20, calendar spec section 10): before authentication, IMAP, POP3 and ManageSieve trace raw input and output as `[redacted]` and redact only the errors that can quote input (imap-proto's BAD errors; POP3 parse errors marked BAD when queued pre-auth); SMTP masks SASL-state reads, reads holding `AUTH` plus whitespace anywhere (joined to the partial request line) and reads up to the line end after a 334 (`SessionData::za_answers_334`); OAuth form bodies are read untraced. This applies to every account, since the account is unknown before authentication. After authentication the rule is whole-session for key accounts (mail spec 10, issue #21): IMAP and POP3 trace a key account's session as `[redacted]` throughout (raw input and output, BAD errors, the details of `ImapEvent::Fetch` and `Store`); SMTP redacts every read of a transaction submitted by a key account (`SessionData::za_key_sender()`) or delivering to one (`SessionData::za_key_rcpt`, set at RCPT by `Session::za_has_key_rcpt` through `Server::za_is_key_rcpt` (`crates/smtp/src/inbound/rcpt.rs`) and noted again at the end of DATA for recipients a milter, hook or script added (`crates/smtp/src/inbound/data.rs`), so a read holding an RCPT and a DATA or BDAT command is redacted for every account, plan 13 ruling R41) and that transaction's milter and spam-filter events (`MilterClient::redact`, `SpamFilterInput::za_redact`); a key account's own Sieve runtime-error reason at delivery (`crates/email/src/sieve/ingest.rs`) is redacted and its `MessageIngest` events carry `[redacted]` instead of the Message-ID; the vacation compile error reason names its position only (`compile error at line N, column M`) for every account.
- Key pinning (its spec section 10, 16-23): pins compared before any item, keyed by normalized address against the freshly read served key; the pinned wrap never reverts; only `contacts/pin` and `contacts/forget` with null create a record under a pinned wrap.
- Mail at rest (its spec section 12, 24-32): every message of a key account is a stub plus a sealed blob whatever wrote it, and a writer that classified the account as ordinary asserts in its batch that no vault record exists; a mail session of a key account exists only with keys, and every read holds the owner's keys or is refused; no threading index, full-text term, spam sample or push payload with content (the search document holds the arrival time and the size); plaintext outside process memory only in the SMTP queue and in the staged blob of an ordinary ingest that failed during provisioning; delivery never reads a session key and never stores in the clear (no served public key: a temporary failure); traces carry no content, header name or value, Message-ID or search term, raw or structured; no raw read of a sealed source (an upload, a message blob or a section of one): it is read through the unsealing reader with the owner's keys or refused; the ordinary-writer assertion, the vacation compile reason and the masking of reads that hold an RCPT and a DATA or BDAT command (plan 13 ruling R41) apply to every account and are invariant 9 exceptions (spec 12's rule 32).
