## What changed and why

**Task 1, the key-trust primitives (spec 3.1, 4.1, 4.4, 7).** `crates/vault/src/keys.rs` gains the two purposes (`AAD_PINS`, `AAD_PRIVATE_KEY_PINNED`), `derive_public_key`, the display fingerprint (`fingerprint_bytes`, `display_fingerprint`, and `parse_fingerprint`, which takes any case and spacing), `WrapMark` and the wrap pair: `wrap_private_key`, and `unwrap_private_key`, which tries the pinned purpose first, then the legacy one, and is `KeyError::Aead` when neither opens. The new `crates/vault/src/pins.rs` holds the pin record of 4.1 (`ZaPinRecord`, `ZaPin`, `PinSource`, `ZaWithheld`, `ZaInstances`), whose `Debug` prints counts only; its stored form (`seal_pin_record`, `open_pin_record`: a big-endian length, the rkyv archive and zero padding to a multiple of 256, sealed under MK with `aad("pins", id)`, decoded with a checked read, any version other than 1 unusable); and its operations: `refuse` gives every refusal a fresh random `refusal_id`, `retire` removes an entry only under the id it consumed, and `ZaInstances` holds 64 keys before it switches to `all`. `PrincipalField::ZeroAccessPins = 151` (`crates/types/src/field.rs`).

**Task 2, storage (spec 4.2, 4.4, 4.5, 5.1).** `crates/common/src/auth/vault.rs` gets one batch builder, `vault_batch_write`, under `vault_commit_store` and `Server::za_vault_commit` (the revision bump, the conditional write and the invalidation), which `za_commit` now wraps (4.5). With a pin write the batch holds the vault assertion, the pin assertion, the vault set and the pin set, in that order, so the ephemeral store's in-place sets cannot apply half a batch (ruling). A pin read asserts `Hash` of whatever bytes are stored and `None` only when nothing is (4.2); the mark is read pinned first (`ZaMark`: `Pinned`, `Legacy`, `Neither`); `za_pin_state` reads the mark only when the record is not usable; `za_pin_transact` makes eight attempts, writes the first-pin or heal batch under a legacy wrap and the pin record alone otherwise, and refuses to create a record under a wrap that opens under neither purpose (ruling); `za_served_public_key` returns the public key of an Active record and nothing else (5.1); `za_normalize_address` is the one normalization (4.3). `assert_is_empty` exempts field 151 while its account exists, and `tests/src/utils/za.rs` gains the store-writer helpers (`substitute_public_key`, `pin_record`, `write_pin_record`, `raw_pins`, `set_raw_pins`, `za_unpin`, the wrap helpers).

**Task 3, the self-check (spec 3.2, 3.3, 4.4).** `za_open_private_key` gave way to `self_check_store` and `Server::za_self_check`: one mark read; the public key derived from the private key and compared with the stored one; on a mismatch the `Unauthorized` trace and one repair batch (the stored key rewritten from the derived one, `key_repaired_at` set when a usable record exists, and the heal's rewrap when that record sits under a legacy wrap); no record is created. A lost assertion re-reads under the eight attempts. `za_private_key` runs it once per session (`once`), `drain_pass` runs it on every session's first pass, items pending or not, and `za_drain` now returns its `PassOutcome`. Case 3.

**Task 4, the fan-out's pin decisions (spec 4.3, 5.1-5.4).** `za_fan_out` takes `ZaSource` (the source document id and UID) and `ZaFanOutKind` (`Change`, `Deletion`, `Redelivery`) and runs in the four phases of 5.2: it resolves each normalized address once, with the served key read fresh from the recipient's vault record (the account cache's `za_public_key` is no longer read), and reads the pin state; it decides every internal recipient against the record and writes the record before any item (first-use pins; refusals with a withheld entry, a refused REPLY's instances recorded by instant; under a pinned wrap without a usable record, fail closed and record nothing); it writes the items; and it retires consumed entries. A refusal is `3.8` (`ITIP_STATUS_KEY_REFUSED`, rank 3) and one `Unauthorized` trace per fan-out with the sender and a count. The PUT create assigns its document id before the fan-out. Hooks `PIN_DECIDE_PAUSE`, `RETIRE_PAUSE`, `PIN_WRITE_FAIL_ONCE`. Cases 1, 9, 16, `rf_2`, `rf_3`; the TZID fixtures use `Etc/GMT-1` (ruling).

**Task 5, the endpoints (spec 5.6, 6.1-6.5).** `crates/http/src/api/contacts.rs` serves `contacts`, `contacts/lookup`, `contacts/pin` and `contacts/forget`, routed by `handle_vault_request` behind the anonymous-request rate limit. Each verifies the password afresh and runs the full self-check first; a private key that opens under neither purpose is the 409 `vault record missing` (ruling). `contacts/pin` pins `Confirmed`, drains while a pass returns `More`, redelivers up to `REDELIVER_BATCH` (32) of the address's entries as current state, and retires the delivered and dropped ones under the refusal ids it consumed. The groupware helpers live in `crates/groupware/src/calendar/pinning.rs`: `za_full_request_for` (the full REQUEST for one recipient), `za_participation_reply` (the recorded instances' current participation, filtered as 6.4 step 2 says) and `za_reply_from`. The `REDELIVER_CLEANUP_PAUSE` hook is reached through a forwarder (ruling). The fix rounds made the listing read the mark before the pin record (ruling), added case 17 (e) for the retried reseal's equal-id branch, and made 17 (d) assert the newer refusal's `3.8`. Cases 2, 4, 6, 7, 8, 10, 14, 15, 17-20, `rf_1`, `rf_4`, `rf_5`.

**Task 6, the SEQUENCE floor and the reconciliation (spec 2 limits 9-10, 5.1, 13 item 4).** The new `crates/groupware/src/calendar/sequence.rs` holds `za_instance_keys` (each scheduling component's `InstanceKey`, computed as `itip_snapshot` computes `RecurrenceId::date`), `za_sequence_floor` (a key organizer's PUT of an existing event raises each component's SEQUENCE to the stored value and adds nothing), `za_reconcile_sequences` (before phase 1 the fan-out's committed clone and every organizer REQUEST and CANCEL get each instance's highest SEQUENCE) and `za_set_sequences` (raises only, ruling). `ZaFanOutResult.sequences` is applied next to the statuses at every call site: the update and create PUTs, the drain's delegating merge, and `contacts/pin`'s step 4 and its retry. The fix round tested the removed instance's maximum, raise-only and instance-key parity with `itip_snapshot`, and gave the floor `event_organizer` as its organizer check. Task 6 also ran the probe of open item 4. Case 12.

**Task 7, the two-item rule and the deletion (spec 2 limit 6, 5.1 items (1)-(2), 5.2 phases 3-4).** In a change, an internal recipient holding an entry for the source gets the full current state (the full REQUEST, or the participation REPLY) before upstream's messages. It is skipped when the recipient's own messages carry the master in a REQUEST or a CANCEL, when the relationship ended, or when nothing is built; a failed full state keeps the entry. A deletion with a message to send retires every entry of the deleted document. An attendee's DELETE that holds an entry for the organizer sends the fork DECLINED (`za_decline_all`, `decline_instance`, without upstream's PARTSTAT gate, ruling), and `ZaDeleteMessage.message` became an `Option`. The fix round adds the decline's organizer to the recipients only when the decline routes, adds a NEEDS-ACTION unit test, and makes case 13 (d) assert its retirement. Cases 5, 11, 13, 21.

**Task 8, coverage and documentation.** `leak::test_pins` scans both accounts while alice's record holds a pin and an entry for `key2+pinaddr-canary@example.com` (an account's own address is in the registry in the clear, so the canary rides in a sub-address, which pins separately, spec 4.3); the key-mode `scheduling` variant asserts that a first-use pin record exists when `assert_is_empty` runs; manual checklist item 15 covers how clients show `3.8`; CLAUDE.md names the new code, hooks, invariants, exemptions and hotspots; api.md in `circulo-account` documents the four endpoints and their flows; then the mutation runs and this note.

## Spec notes

- Spec 7 gives the pin record's length prefix as a big-endian `u32`, while 4.1 says the plaintext is padded "as release 1 pads bundles". The latter governs the padding only: release 1's `seal_bytes_as` (`crates/groupware/src/calendar/seal/tree.rs:243`) writes its length little endian, and the pin record (`crates/vault/src/pins.rs:134`, `:151`) is big endian, as spec 7 says.
- Case 20's outcome no longer depends on the drain once revision 7 recorded instances, so its direct assertion, "contacts/pin drained before building", is what pins M71.
- calcard 0.3.14 resolves a VTIMEZONE only by name (`Tz::from_str` on the TZID, X-LIC-LOCATION or a Microsoft id; calcard `src/icalendar/timezone.rs:84-104`), never from its offsets, so a custom-named zone is floating on both sides: the fork's `InstanceKey` agrees with `itip_snapshot` and the drain, and a RECURRENCE-ID in a custom-named zone never matches the UTC form of the same instance (the CANCEL keeps old+1). This is why the TZID fixtures of Tasks 4 and 6 use `Etc/GMT-1` (ruling).
- `refused_instances` (`crates/groupware/src/calendar/fanout.rs`) records `all` when a refused REPLY has no snapshot, the over-approximation (ruling); upstream's REPLY builders always produce one.
- The approved spec still names `za_open_private_key` (spec lines 209, 217, 356); the code calls the unwrap `unwrap_private_key` (`crates/vault/src/keys.rs:332`) and the self-check `za_self_check` (`crates/common/src/auth/vault.rs`, over `self_check_store`).
- The deletion retires its entries in its fan-out, before the delete batch commits (`crates/dav/src/calendar/delete.rs:258-276`); a failed `commit_batch` leaves the event with its entries gone. This follows spec 5.4's order, as the change path does, and is a stated loss (Task 7).
- Task 5 added a trace string the plan did not list: `zero-access: withheld entry not redelivered` (`crates/http/src/api/contacts.rs:454`, `:471`), with the account id and document id.
