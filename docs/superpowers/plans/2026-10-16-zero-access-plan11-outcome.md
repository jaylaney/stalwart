## What changed and why

**Task 1, the spec.** The invitations spec now says what the code does after this plan and records Jay's decisions of 2026-10-16. Section 5.1: the sending state follows the calendar owner's key status (`ItipSendStatus::resolve` takes `owner_is_key`; JMAP callers pass `false`); in release 2 only the owner writes to a key account's calendar, so the rule describes the code and stays right when sharing arrives. Section 5.4: a key account's create passes its UID creation lease to the fan-out as the fence; items delivered before a takeover are an accepted, bounded residual (the recipient ends on the committed token, a reply sent between the two items is dropped once, and a 503 with no successor heals on the client's resend); compensating deletion of delivered items was rejected (recorded in section 14); updates and deletes take no lease, since their commit is fenced on the event's stored archive. Section 6.2: the per-pass cap (`DRAIN_PASS_CAP`, 32) ends a pass without a deferral or a cursor move, and an item that fails `DRAIN_ITEM_FAILURE_LIMIT` (3) times in a session is skipped for that session with later items of its UID left pending with it; neither holds the cursor. Section 6.5: the failure limit bounds transient retries, and `MissingUid` and `NoSchedulingInfo` are iTIP-level rejections kept as history. Section 10: a recorded private-key failure skips the drain for the rest of the session by a permanent deferral (a new session's `SessionKeys` retry the unwrap), while a store error reading the record defers by `DRAIN_RETRY_SECS`; a store error before the drain's match defers like one after it. Sections 11 and 13 name the hooks, the tests and the constants. Manual checklist item 14 covers a client that strips SEQUENCE from the attendee's copy.

**Task 2, the PUT create's fence (spec 5.4).** The create branch of the CalDAV PUT handler (`crates/dav/src/calendar/update.rs`) passes `za_lease.as_ref().map(|(lease, _)| lease.lease())` to `za_fan_out`, the fence plan 10's fix wave added for the drain's delegating merge, so a creator whose lease was taken over writes no recipient item after its successor's. A lost fence inside the fan-out (an assertion failure) takes the lease out and returns `za_lost_create_fence`, the helper extracted from `za_commit_create`'s assertion-failure arm, which both sites now share. A recipient failure that is not a lost fence (quota, size limit) still becomes a `SCHEDULE-STATUS` and a 201 (`fanout::test_failures`), and any other error of the call returns as before. Lease cases (b) and (b') now assert that the held create delivered nothing. With the fence at the fan-out, no test reached `za_commit_create`'s own lost-fence arm, which is the only fence for a create without internal attendees (ruling R3); the fix round added `COMMIT_PAUSE` (test mode, immediately before the key account's leased create commits) and lease case (b''), which parks a create with no attendees past its 1-second lease, takes the lease over and asserts 412 with a planted copy and 503 without.

**Task 3, the drain limits (spec 6.2, 6.5, 10).** `drain_pass` now enumerates through `enumerate` and maps a store error there to the same `DRAIN_RETRY_SECS` deferral as an item error. `drain_items` returns a `PassOutcome` (`Complete`, `LeftPending`, `More`, `Suspended`): a recorded private-key failure is `Suspended` and defers the session by `PERMANENT_DEFERRAL` (`u64::MAX`), so no later request of the session enumerates the inbox; a store error reading the key is not recorded and keeps the ordinary backoff. An item's own error (`drain_item` returning `Err`, ruling R2) counts toward `DRAIN_ITEM_FAILURE_LIMIT`; at the limit the item is skipped for the session with one trace, and the pass goes on. `drain_item` checks `blocks_uid` after the UID snapshot, so a later item of a skipped item's UID comes back `Waiting` and a CANCEL never overtakes its REQUEST. The fix round (ruling R6) added the `waiting` set to `PassState`: a waiting item is recorded there, does not count toward the cap (only attempted items, done, left pending or failed, count), and is filtered out of later passes with the skipped ones, so 32 or more items waiting behind a skipped one no longer make every pass return `More` on the same items. The test module `tests/src/za/drain_limits.rs` has five steps. Step 1 cannot see the permanent deferral through pending counts, because the recorded unwrap failure keeps every later pass of the session suspended either way; it sets the zero backoff before the failing pass and uses the enumeration hook as a probe: `DRAIN_ENUMERATE_FAIL_ONCE` set before the failing session's second request must still be set afterwards, since a pass that ran would have consumed it (ruling R4). Step 2 is the enumeration error's deferral, step 3 the skipped item and the CANCEL that waits behind it (its own item id asserted still pending, ruling R7), step 4 the cap with the default backoff in force. Step 5 skips a REQUEST, plants 33 later items of its UID and an unrelated item, and shows that the unrelated item drains with the default backoff in force and a fresh session drains everything; its probe rewrites the skipped item and one waiting item undecodable and asserts both survive a pass, since a pass that re-opened them would delete them under spec 6.5 (ruling R8).

**Task 4, the deferred tests.** Each input the plan 10 reviews left uncovered is pinned where the code lives: `test_reply` step 10 plants a REPLY with key2's real token as if key3 had sent it and shows it is history for a sender mismatch; `test_adoption` step 1 shows the old token is a forgery after a re-add; `test_lease` cases A and E assert that session 2 waited at least a second on the lease; `test_errors` step 3 asserts that an orphan REPLY creates no event; `drain::test` step 6 shows that key2's PROPFIND of key1's data drains key2's own inbox; `leak::test_drain` scans key1 while the reply is pending and checks the task queue after it; the key-mode `scheduling` variant checks the moved canary in the stored archive; and the unit test `a_doubled_attendee_keeps_the_union_of_its_delegators` pins the DELEGATED-FROM union of an address listed twice in one instance. `ItipSnapshot::attendees` is a hash set iterated in a per-process random order, so the first version of that test let the "last line wins" mutation survive in some runs; the fix round gives the doubled attendee two different delegators and asserts that a merged attendee carrying either one alone is not new, which fails any single-line rule in every order (ruling R9).

## Final review

The whole-branch review (`b13c0d64..82d25695`, opus, `final-review.md` in the plan's ledger: 0 critical, 1 important, 9 minor, "with fixes") and its rulings:

- I1 (important), fixed in `08eb37d3`. `enumerate` has already read and unarchived every pending item, so a failure of `drain_item`'s re-read, unarchive or deserialize is a transient store error on a sound archive, yet it counted toward `DRAIN_ITEM_FAILURE_LIMIT` with no UID; an item whose third failure came there was skipped with `None`, blocked nothing, and the same pass filed the later CANCEL of its UID as history, so a fresh session imported the REQUEST and the attendee kept a live copy of a cancelled event. Ruling: such a failure aborts the pass with the ordinary backoff, as an `enumerate` error does, and is not counted (`ItemFailure::counts`, `false` for `no_uid`, `true` for every failure `item_outcome` returns); `PassState::record_failure` also keeps the first UID any of an item's failures named (`PassState::uids`), so a skip after mixed failures still blocks its UID. Spec 6.2 now says so. `drain_limits` step 6 (`tests/src/za/drain_limits.rs`): a REQUEST whose re-read fails (`DRAIN_READ_FAIL_ITEM`) on three passes keeps its CANCEL pending and creates no copy; with the hook cleared, the same session imports the REQUEST and applies the CANCEL, in order. M50 kills the rule.
- m1-m4, fixed in the documentation commit: spec 6.5's transient bullet defers to 6.2's definition of a counted failure (m1); 6.2's cap counts attempts and says waiting items are not re-opened in the session (m2); spec 11 points lease cases (b) and (b') at `uid_lease.rs`, names (b'') and `drain_limits` steps 5 and 6 (m3); 5.4 states that a successor with a lower SEQUENCE is rejected by upstream's merge and the recipient keeps the loser's token until the organizer's next message (m4).
- The triage's "fix before merge" lines, fixed in the documentation commit: 5.4 covers a create's commit failing for another reason; the R2 clause is in 6.2; CLAUDE.md names `drain_limits.rs`, the two `dav/src/calendar` hotspots and the release 2 status; the plan 10 note's pointer line names the Task 3-5 test minors Task 4 resolved. The cosmetic lines folded into the same commit: the spec 11 hooks sentence's extra "and", the spec 13 Names bullet, this note's line on M44 and M46, the R4/R8 kill-line sentence under "Rulings", CLAUDE.md's back-to-back parentheticals.

## Deferred findings

What stays open after this plan:
- (plan 10, pr-fix2-review.md M1) A delegate's PARTSTAT reset to NEEDS-ACTION without a DELEGATED-FROM gain (a decline followed by the delegator's per-occurrence accept, whose override copies the delegate's stale line): the delegate is not asked. An upstream merge-semantics question that upstream shares; see the plan 10 note.
- (plan 10, Task 2 review) Every DAV request of a key account runs one change-log since-query and any inbox change makes the next request read every inbox archive: a pending-item index if inboxes grow. The cap multiplies that cost (plan 11 final review m7): draining P pending items in an inbox of N archives takes ceil(P/32) passes of N reads each, where it took one.
- (plan 10, Task 3 review) The drain test module (`tests/src/za/drain.rs`) is large enough to split (helpers to utils, the reply tests to their own file); it grew again in this plan.
