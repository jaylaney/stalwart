## Decisions Jay made (not in the code, partly in the spec)

- Fork Stalwart rather than build from scratch; AGPL publication of the fork
  accepted. The "separate vault service" middle path was judged an outside
  possibility, not the plan.
- Trust model A: operator cannot read data at rest or when the user is logged
  out; native CalDAV/IMAP clients unmodified; the running server holds
  plaintext during a session, and product copy must say so.
- Release 1 is calendar only, personal calendars, no invitations. Later, in
  order: invitations between users, invitations by email, mail, JMAP
  calendars and a web client, search. Invitations will keep attendee
  addresses encrypted (Proton model: per-attendee random token plus RSVP
  status in the clear, event key wrapped to each internal attendee's public
  key). Jay accepted the residual leak (attendee count, RSVP status, linkage).
- Recovery key at signup, no operator escrow.
- The account API lives in the fork; the signup/account web page goes in a
  **separate repository**. Jay said "let me know when we need to start another
  repo": that moment is when plan 1's eight `/api/vault/*` endpoints exist.
- JMAP calendars are gated off for key accounts in release 1; Jay is "fine
  with waiting".
- Judgment calls Jay confirmed: store the plaintext iCalendar length as the
  visible event size; bind collection bundles to the account only (no reseal
  on copy).
- The product is built **without the `enterprise` cargo feature**. That code
  (the `scim` crate and every `cfg(feature = "enterprise")` block) is licensed
  only under the Stalwart Enterprise License. Without a license key those
  features are inert at runtime anyway, so nothing functional is lost for
  release 1. Jay asked for this after a viability discussion on 2026-10-06.

## Facts about the codebase that shaped the plans

Verified by reading the source on 2026-10-06. The plans quote the exact code;
this is the short list of things that would surprise someone.

- Six files in `crates/registry/src/schema/` and `crates/trc/src/event/enums.rs`
  are generated by a tool that is **not public** (checked the repo history,
  all 29 Stalwart Labs repos, crates.io, GitHub code search, docs). The shipped
  `resources/schema/schema.json.gz` is a UI export, not the master definition.
  Consequence: no new registry settings and no new `Permission` variants.
  Key-cache limits are environment variables (`ZA_KEY_IDLE_SECS`,
  `ZA_KEY_MAX_AGE_SECS`, `ZA_KEY_MAX_ENTRIES`); `setup-token` reuses
  `Permission::SysAccountUpdate`; no new `trc` event variants either.
- The marker secret `$za$` cannot be stored through JMAP, SCIM or the
  `AccountPassword` singleton (the mapping validators treat it as a weak
  plaintext password). It can only be written by a direct
  `registry().write(..)`, which is what the setup-token endpoint does. If the
  marker ever reached `verify_secret_hash`, it would return
  `Err(AuthEvent::Error)`, so the auth router diverts it beforehand.
- Upstream's HTTP auth cache is keyed by the raw `Authorization` header value
  (reversible base64 of the password); plan 1 replaces the key with a keyed
  BLAKE3 fingerprint.
- `credential_version` on access tokens is `xxh3(secret)`, constant for the
  marker; plan 1 derives it from the vault generation instead.
- `fetch_dav_resources` creates the default calendar as a side effect, so the
  setup eligibility check reads archive keys from the store directly.
- `tests/src/utils/cleanup.rs::store_assert_is_empty` scans the whole
  Principal property subspace; vault records live there, so plan 1 Task 11
  adds an exemption and `za_tests` destroys its key accounts at the end.
- The `tests` crate enables `enterprise` on `store`, `directory` and
  `coordinator` for upstream's own test modules; leave it.
- `webdav_tests` is one test function running sub-modules in order against
  one server; there is no env-based subset selection. CI's `test.yml` is
  manual-trigger only and does not run the CalDAV suite; plan 3 adds jobs.
- Stalwart Labs' libraries (`calcard`, `mail-parser`, `mail-auth`,
  `mail-send`) are Apache-2.0 OR MIT; the server is AGPL-3.0-only OR SEL.

## Crate API facts verified from sources (no compiler was available)

- `argon2 0.6`: `Params::new(m_cost_kib, t_cost, p_cost, Some(32))`,
  `Argon2::new(Algorithm::Argon2id, Version::V0x13, params)`,
  `hash_password_into(pwd, salt, out)`.
- `hkdf 0.13` with `sha2 0.11`: `Hkdf::<Sha256>::new(None, ikm)`,
  `expand(info, &mut okm)`.
- `chacha20poly1305 0.11` (aead 0.6): `XChaCha20Poly1305::new_from_slice(key)`,
  `XNonce::from([u8; 24])`, `cipher.encrypt(&nonce, Payload { msg, aad })`,
  `decrypt` likewise; default features include `alloc`.
- `x25519-dalek 2.0.1`: `StaticSecret` needs the `static_secrets` feature;
  `StaticSecret::from([u8; 32])` then `PublicKey::from(&secret)`; avoid its
  `rand_core 0.6` RNG by generating bytes with `rand::random`.
- `rand 0.10`: `rand::random::<[u8; N]>()`, `rand::rng()`, `RngExt`.
- `base32 0.5`: `encode(Alphabet::Rfc4648 { padding: false }, ..)`; decoding
  26 unpadded characters yields exactly 16 bytes.
- `blake3 1.8`: `blake3::keyed_hash(&key, data)`.
- `calcard 0.3.14` (`rkyv` feature on): `ICalendar { components }`,
  `ICalendarComponent { component_type, entries, component_ids }`,
  `ICalendarEntry { name: ICalendarProperty, params: Vec<ICalendarParameter>,
  values }`, `ICalendarParameter { name: ICalendarParameterName, value }`;
  `ICalendarProperty::Other(String)` for `X-` properties; the writer emits an
  `Other` text property as `NAME:escaped-text`, so base64 carriers serialize
  cleanly. Parse with `calcard::Parser::new(text).entry()` matching
  `calcard::Entry::ICalendar(ical)`.
