# Fable review of the upstream v1.0.3 merge plan (revision 2)

Reviewed: `docs/superpowers/plans/2026-11-05-upstream-1.0.3-merge.md` at commit `53df5359f`
on branch `upstream-1.0.3` (the fork at `bbabd0847` plus the two plan commits). Plan line
numbers below refer to that revision.

How I worked: reading only. Evidence comes from the worktree at `bbabd0847` (cited `fork:`),
upstream's tags `v1.0.1` and `v1.0.3` (`v1.0.3:` paths, `git show`), the raw merge result
`git merge-tree --write-tree bbabd0847 v1.0.3` (tree `979b17c25e…`, cited `merge:`; its line
numbers match the plan's `trial:` numbers), the six analysis reports A–F and the Codex review,

Severity: critical = an invariant breaks or the merge is misqualified; important = a step
silently does the wrong thing, a test cannot work or cannot fail as claimed, or the suite
hangs; minor = a correction that keeps the plan executing as written.

## Findings

### F1 — important, high: the blob-codec cases remove a `SymmetricKey` while blobs still depend on it, and the harness's `Server` snapshot never sees the key

Plan lines 504, 513–531 (Task 8 `test_blob_recode_keeps_sealed`, `leak::test_codec`) and
481–483 (Task 7, the scanner reads through `test.server.get_blob`).

Evidence:
- `fork:tests/src/utils/server.rs:497-499`: `TestServer::reload_core` rebuilds `self.server`
  from `inner`; until it is called, `test.server` is the `Server` built at suite start, whose
  `core.blob.keys` is the empty keyring. `fork:tests/src/utils/registry.rs:264-267`
  (`reload_settings`) reloads the running server's core, not that snapshot.
- `fork:tests/src/utils/storage.rs:215-262`: `wait_for_tasks` (which `wait_for_delivery`,
  `destroy_key_accounts` and most modules call) loops until no search-index partition "still
  holds queue entries, a queued-work marker or a failure status", with no deadline.
- `v1.0.3:crates/services/src/index_queue/document.rs` (merge `:46`): an ordinary account's
  index build reads the blob with `server.get_blob`; a decrypt error is an `Err`, not the
  missing-blob `Ok(None)` skip, so the partition fails and retries with backoff
  (CLAUDE.md: "a failing partition retries with backoff ... and never fails terminally").
- `v1.0.3:crates/services/src/task_manager/tasks/blob_recode.rs:61-62`:
  `TaskBlobRecodeCompression::Disable` means `CompressionAlgo::None` for every blob
  `user_blob_hashes` selects (every Email, SieveScript, FileNode and queue blob of every
  account on the server), and `:69-74` `Encrypt(target)` names a key id the plan omits.

Failing scenario 1 (`leak::test_codec`): the module sets `Email.blobEncryptionKey`, reloads,
delivers its canaries, and scans with `test.server.get_blob(...)`. `test.server` still holds
the empty keyring, so every encrypted blob answers "blob does not decode" (the scanner's
violation branch, `fork:tests/src/za/leak.rs:1527-1530`): the case fails on a correct
server, and M8's expected failure is indistinguishable from it.

Failing scenario 2 (either case): the key is removed (the `SymmetricKey` destroyed and the
setting restored) while `codec-leak-plain`'s messages, or any blob the module wrote while the
key was set, are still encrypted under it or still queued for indexing. The next index pass
of the Email partition fails with a decrypt error and retries forever; the next
`wait_for_delivery` or `wait_for_tasks` anywhere in the suite (the mail modules that follow,
`destroy_key_accounts` at the end) never returns, and the za suite times out with no
failing test named.

Failing scenario 3 (`test_blob_recode_keeps_sealed`): `BlobRecode { Disable, Disable }`
"restores trailer `0x00`" for the one blob under test by rewriting every linked blob on the
server uncompressed, and leaves the server's blobs in a state no other test expects (the
leak scans' raw-value search over `Blobs`, `fork:tests/src/za/leak.rs:1332`, was blind to LZ4
and now reads plaintext in ordinary accounts' blobs).

Correction:
- In both cases call `test.reload_core()` after each `reload_settings` (after the key is
  set and after it is removed), and state it in the plan; the same holds for any test-side
  read of `test.server.core.email.gateway` in Task 5's module.
- Fix the order: wait for the accounts' index queues (`wait_for_index_queue`) and for the
  recode's shard tasks, then clear or destroy the module's messages (and recode back with
  `encryption: Disable, compression: Keep`), and only then destroy the `SymmetricKey` and
  restore the settings. Assert the encrypted bit is cleared rather than trailer `== 0x00`.
- Name the key id in `Encrypt(target)`, and record in the outcome note that the recode
  touched every account's blobs.

### F2 — important, high: the harvest absence checks race the spawned worker, so M3 and M3b can pass under mutation

Plan lines 347–357 (`harvest_skips_key_accounts`, `harvest_loses_to_provisioning`) and
572–573 (M3, M3b).

Evidence:
- `v1.0.3:crates/email/src/message/delivery.rs:327-330`: `spawn_harvest` runs after the
  recipient loop; `v1.0.3:crates/common/src/gateway/harvest.rs:73-82`: it takes a permit
  from `inner.data.harvest_tasks` (a `Semaphore`, `v1.0.3:crates/common/src/config/inner.rs:114`)
  and `tokio::spawn`s the worker, which parses the message, evaluates `harvestKeys`, looks the
  sender up and writes the row (`harvest.rs:84-150`). Nothing in the delivery path waits for it.
- `harvest.rs:113-119`: a later message from the same sender whose fingerprint the entry
  already `knows` within `LAST_SEEN_RESOLUTION` is skipped (`continue`), so a second delivery
  from `dmarc-ac-race@remote.test` writes no second row.

Failing scenario (M3b): `za_harvest_kept(&status)` is replaced by `true`. The stale attempt
spawns the worker; `wait_for_temporary_failure` returns as soon as the queue holds the
failure; the case's "no `ExternalPublicKey` for the sender" query runs a few milliseconds
later and may precede the worker's write. Then the control (`za_vault_delete`, the retry)
finds the row already there and writes none: "exactly one row" holds. The mutation passes.
`harvest_skips_key_accounts` has the same shape: "once the control's row has appeared" orders
nothing between two independently spawned workers.

Correction: give the module a sync point and name it in the plan. After each delivery
returns, poll `test.server.inner.data.harvest_tasks.available_permits()` back to
`MAX_HARVEST_TASKS` (the permit is dropped when the worker ends, `harvest.rs:78-81`), then
assert the absence of the row and of `KeyHarvested`/`KeyChange` events; in
`harvest_loses_to_provisioning` do so before `za_vault_delete`, and keep the control's
assertion as "a row exists after the retry", not "exactly one".

### F3 — important, medium: `server_wide_tasks_do_not_block_setup` cannot hold its fixture, and a not-due task hangs every wait helper

Plan lines 514–516.

Evidence:
- `v1.0.3:crates/services/src/task_manager/tasks/external_public_keys.rs:81-83`: with the
  gateway off, `ExternalPublicKeyMaintenance` returns `Outcome::Done` at once, so a task
  queued "now" is consumed and removed before `setup-token` is called; the case then proves
  nothing for that variant.
- `fork:tests/src/utils/storage.rs:233-244`: `wait_for_tasks` (the non-`skip_not_due` form
  every module uses) waits for a task whose due time is an hour away.

Failing scenario: the case queues `BlobRecode` due in an hour and `ExternalPublicKeyMaintenance`
due now, then any helper in the case or the rest of `mail::fence` calls `wait_for_delivery`
before the tasks are destroyed: the suite blocks for an hour (the workflow's 120-minute
timeout then ends it).

Correction: create both tasks with a future due time (or hold `TASK_CONSUMER_PAUSE` for the
case), call no wait helper while they exist, destroy them with `x:Task/set` before returning,
and say so in the plan.

### F4 — minor, medium: decision 6's one line has no test or mutation row

Plan lines 36, 104 ("one line (decision 6); new test"), 241–244, 262–264.

Evidence: upstream's default-role branch clears `access_tokens` and wipes `http_auth`
wholesale (`merge:crates/common/src/cache/invalidate.rs:718-720`); the epoch is read and
re-read only by the loaders (`fork:crates/common/src/auth/access_token.rs:347-390`,
`cache/principals.rs:447,698`), and no unit or integration test names `account_epoch`
(`grep` over `tests/src` and `crates/common/src/**/*restored*`: none).

Scenario: the implementer omits the `fetch_add` or places it after `clear()`; Task 3's
`default_role_edit_reverifies_key_sessions` still passes, because upstream's wipe alone
produces every observation it makes. The plan's "new test" claim for A12 is then false, and
Task 9's mutation table has no row for it.

Correction: either add a mutation row (the line removed; a loader parked with the existing
pause hooks across the role edit, asserting the parked token is not republished), or state
in the table and the outcome note that decision 6 is adopted untested.

### F6 — minor, high: porting `system::crypto` needs a dependency the plan does not list

Plan lines 184 (Task 2 edits `tests/Cargo.toml` for `mail-auth` only) and 486 (Task 7
ports `system::crypto` "to upstream's public key parsing").

Evidence: `fork:tests/src/system/crypto.rs:15` imports `email::message::crypto::EncryptMessage`

dev-dependencies if the port keeps the parsing or encryption assertions, or removes the case

### F7 — minor, high: R1's residual is wider than "a Sieve script that discards"

Plan lines 386 and 648.

Evidence: `v1.0.3:crates/email/src/sieve/ingest.rs:874-891`: `sieve_script_ingest` answers
`Ok` whenever no delivery was attempted (`last_temp_error.is_none()`), so a script that only
redirects, or rejects, yields `Ok` with no batch and no fence; and `Ok` when any one
`fileinto` delivered, so a script filing into two mailboxes whose second batch lost the fence
keeps the harvest.

Correction: word the residual as "an ordinary-classified recipient whose active Sieve script
runs no fenced ingest (discard, redirect-only, reject) or whose first `fileinto` committed
before setup, while setup completes".

shows the existing pattern: the module lists and destroys the grants it created.

### F9 — minor, low: the spam rules pin `v3.0.4` is a premise the branch cannot check
