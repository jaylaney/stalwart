The new R1 rule rejects every error and no-write outcome before the account lookup.
`email_ingest` produces its committed result only after `write_batch` succeeds
(`v1.0.3:crates/email/src/message/ingest.rs:246–264`); duplicate/no-write results retain

### R8 — [P2] Clear the ordinary control's previous index document before expecting none

**Revised plan: 587–591.** The revision correctly replaces the obsolete retry expectation,
but now requires the missing-blob pass to leave no ordinary Email search document. The
existing positive control has already indexed that message
(`tests/src/za/index_task.rs:561–562`). Its `delete_blobs_and_requeue` helper deletes only
the blob and queues another index pass; it does not remove the existing search document
(`:565–580`). The plan explicitly clears the key account's previous document, but not the
ordinary account's.

Upstream's missing-blob skip does not remove an older search document. It calls
`nothing_to_index`, which only emits an event; with no document or deletion, `flush`
returns immediately (`v1.0.3:crates/services/src/index_queue/index.rs:359–370,457–464,490–491`).
Consequently the new absence assertion still fails on the intended implementation.

**Correction:** After retaining the ordinary positive-control assertion, remove that
account's existing search document before deleting the blob and requeuing, just as the
plan now does for the key account. Then an empty ordinary index and a recreated ids-only
key document distinguish the two paths. Alternatively, explicitly test preservation of
the old ordinary document while separately proving no replacement was produced.

### R11 — [P2] Recode the fixture blob before deleting its message link

**Revised plan: 565–569 and 585.** The new teardown destroys the case's messages before
recoding back, but `test_blob_recode_keeps_sealed` must subsequently observe the original
blob with its encrypted bit cleared. Once message unindexing completes, it removes the
blob's document link (`crates/email/src/message/index/metadata.rs:39–57`).

The recoder does not enumerate every physical blob. `user_blob_hashes` selects committed
blobs with qualifying document, queue or archived-item links; an unlinked blob and an
ordinary temporary hold are excluded
(`v1.0.3:crates/store/src/write/blob.rs:328–344,357–374`). This suite does not enable
deleted-item archival by default (`tests/src/utils/server.rs:384–386` and
`v1.0.3:crates/registry/src/schema/structs_impl.rs:12455–12458`). If unindexing finishes
before the recode shard enumerates, the fixture blob remains encrypted or is purged, and
the required cleared-bit assertion cannot pass. The lack of a drain between destruction
and recode also makes the result depend on scheduling.

**Correction:** Keep the message linked while recoding back, wait for all recode shards,
and assert its encrypted bit is clear. Then destroy and drain the messages while the key
is still available, and finally remove the key and restore/reload settings. Do not rely
on recoding already-unlinked blobs as proof that it is safe to retire the key.

### R12 — [P3] Retain the lockfile edge added by the direct crypto dependency

**Revised plan: 535.** The instruction to add `crypto` to `tests/Cargo.toml` says the
lockfile does not change because this is a workspace path. Cargo records dependency edges
for workspace packages too. The current `tests` entry has `coordinator` followed by `csv`,
with no `crypto` (`Cargo.lock:8740–8754`), and Task 2 resolves the manifest before Task 7
adds this direct dependency. Cargo must add `crypto` to that package's dependency list,
even though the crypto package itself is already present.

**Correction:** Include `Cargo.lock` in Task 7's ownership, retain Cargo's generated
dependency-list change, and verify the result with `--locked`. Do not discard that change
as unrelated dependency drift.

### R1 — [P1] Use ingest's actual classification to authorize harvesting

**Revised plan: 338–339 and 382–385.** Rejecting `AssertValueFailed` closes the case
where ingest reads the account as ordinary and its commit subsequently loses to setup.
It does not close the window between the harvest helper's lookup and ingest's independent
account lookup.

The remaining sequence needs no active Sieve script:

1. `za_harvest_allowed` reads the recipient as ordinary and returns `true`.
2. Setup completes while delivery awaits `sieve_script_get_active`, before ingest reads
   the account (`v1.0.3:crates/email/src/message/delivery.rs:205–214`).
3. Ingest now reads a key account and takes the sealed path
   (`crates/email/src/message/ingest.rs:280–291`). A successful sealed delivery returns
   `Ok`, which the proposed `za_harvest_kept` accepts.
4. The retained flag starts upstream's harvest, writing the sender key/sightings and
   tracing header From/fingerprint despite this being a key-account delivery.

Pending setup also escapes the rule: when no served public key exists, the key path
returns `Store::UnexpectedError` (`crates/email/src/message/za/ingest.rs:93–107`). That
is not `AssertValueFailed`, the sole error recognized by `is_assertion_failure()`
(`v1.0.3:crates/trc/src/event/mod.rs:224–225`), so it also authorizes harvesting.
The downstream persistence and tracing are unchanged from the original R1 evidence.

The Sieve-discard residual at revised line 386 does not cover either path. The new test
at 353–357 parks after ingest has already read an ordinary classification, so it cannot
exercise this earlier interleaving.

**Correction:** Make harvest eligibility follow the same classification and provisioning
guarantee as the ingest that actually ran, with an explicit safe rule for outcomes that
never reached a fenced commit. Add a pause between the harvest lookup and ingest's account
read, and test both pending-setup refusal and successful sealed delivery. Neither may
contribute a harvested row or header-bearing harvest event. Keep the new assertion-failure
case as coverage of the original, later interleaving.

### R8 — [P2] Port the existing missing-blob control as well as adding a new test

**Revised plan: 524–526, together with 434–438.** The plan adopts upstream's missing-blob
`Ok(None)` skip and adds `test_missing_blob_skipped`, but leaves an existing test expecting
the opposite outcome. `index_task::test_attachment_indexer` deletes an ordinary message's
blob and waits up to ten seconds for its partition to enter retry, panicking if it does
not (`tests/src/za/index_task.rs:589–601`).

Under the planned implementation, the missing blob returns `Ok(None)`
(`v1.0.3:crates/services/src/index_queue/document.rs:35–50`), which the worker treats as
nothing to index rather than a failed partition
(`v1.0.3:crates/services/src/index_queue/index.rs:351–371`). The old test therefore times
out. It runs early in the required ZA suite (`tests/src/za/mod.rs:211`), so the new test
cannot substitute for porting this existing expectation. This omission was discovered
while checking the attachment fixture referenced by the revised M7 instructions.

**Correction:** Explicitly assign the existing case's port to Task 8 and record the
upstream-driven expectation change in the ledger. Change its ordinary negative control
to verify successful skip, preserving the ordinary attachment positive control and the
key-account no-blob-read guarantee. Ensure the key assertion proves an ids-only document
is produced, rather than merely observing an index document left from an earlier pass.

### R9 — [P3] Allow M7's earlier detector in the full ZA suite

**Revised plan: 569 and 577.** The plan requires the whole suite and names
`mail::fence::superseded_index_write_loses_to_provisioning` as M7's failing test. Removing
the inline fence is already detected by the earlier `index_task::test_mid_pass_provisioning`:
its messages are plain text (`tests/src/za/index_task.rs:934–942`), and after provisioning
between chunks it requires the next chunk to fail and enter retry (`:1060–1096`). Without
that fence, its retry wait times out (`:806–813`).

The suite calls this detector at `tests/src/za/mod.rs:213`, before `mail::fence` at 217,
so the prescribed run cannot reach the named later detector. This is an attribution error,
not a lack of mutation coverage. The new RTF attachment fixture does exercise the separate
`spawn_blocking` return for M7b.

**Correction:** Name the earlier existing test for M7, or explicitly accept an earlier
equivalent detector. No suite reordering or broader test changes are necessary for this.

### R10 — [P3] Remove invalid JSON escapes from the cohort-entry example

before its backticks. Backslash-backtick is not a JSON escape. Copying the supplied object

**Correction:** Remove those two backslashes or omit the backticks. Parsing the extracted

## Findings

### R1 — [P1] Make key harvesting obey the provisioning fence

**Plan: 317 and 354.** The proposed `za_harvest_allowed` helper checks the recipient's
current classification before ingest, but upstream remembers `harvest_message` before
calling ingest and spawns harvesting even when that delivery fails
(`v1.0.3:crates/email/src/message/delivery.rs:198–205,327–329`). The boolean does not
authorize the later persistence safely across provisioning.

A concrete failing sequence is: enable the gateway; send a DMARC-pass message with a
valid Autocrypt key to a newly created ordinary account; park ingest after its ordinary
classification; provision the account; then resume. The mail batch correctly loses its
vault-record assertion, but the already-true harvest flag starts the background worker.
That worker stores the sender's key and sightings and emits its header From and fingerprint
after the account has become a key account. It receives no recipient account id and its
registry write has no recipient vault assertion
(`v1.0.3:crates/common/src/gateway/harvest.rs:73–84,128–142` and
`v1.0.3:crates/common/src/gateway/store.rs:253–269`).

The existing pause and provisioning fence are at
`crates/email/src/message/ingest.rs:280–286,746–751`; the exact provisioning ordering is
already exercised by `tests/src/za/mail/fence.rs:534–558`. The plan retains those hooks,
but its new gateway tests cover only stable key/plain classifications. A new persistent
registry row and header trace are outside the accepted SMTP-queue/staged-blob residual
(`docs/superpowers/specs/2026-10-20-zero-access-mail-design.md:1385–1401`).

**Correction:** Specify provisioning-safe harvest authorization through its asynchronous
persistence and tracing, preserving the agreed ordinary and mixed-recipient behavior.
Add a deterministic gateway-enabled provisioning-race case using the existing ingest pause,
asserting no harvested row or header-bearing harvest event from the rejected ordinary
attempt, and a sealed retry. A second unguarded boolean lookup alone still leaves a
check/write window. This is a source-established counterexample to the proposed gate;
the merge and regression test have not been executed.

### R2 — [P2] Restore the upstream lockfile by ref after committing the raw merge

**Plan: 159 and 178–184.** Task 1 stages and commits the conflict markers. Task 2 then
uses `git checkout --theirs Cargo.lock`, but staging has already replaced Git's conflict
stages with a normal stage-0 entry. The command therefore does not recover the upstream
lockfile: it leaves the committed markers in place, and the following `cargo metadata`
cannot parse the lockfile.

An isolated temporary Git repository reproduced this sequence: after committing a file
containing conflict markers, `git checkout --theirs Cargo.lock` exited 0 with
`Updated 0 paths from the index`; the markers remained and `git ls-files -u` was empty.
This is a silent failure of the prescribed resolution command, not an objection to the
chosen raw-merge commit workflow.

**Correction:** In Task 2, restore from the verified target explicitly, for example
`git restore --source=v1.0.3 --worktree -- Cargo.lock`, before regenerating and checking it.

### R3 — [P2] Force a transaction split in the iTIP merge mutation fixture

**Plan: 276–286 and 535.** M6 removes only the provisioning fence before `update_full`
and requires `forward_race_imip_merge` to fail. The existing fixture uses a small invitation
and never enables `ForceCommitSplit` (`tests/src/za/mail/fence.rs:811–866`). Although
`update_full_at` calls `commit_point()` (`crates/groupware/src/calendar/storage.rs:212–217`),
that call is a no-op below the 5 MB/1,000-operation thresholds unless the forced-split hook
is enabled (`crates/store/src/write/batch.rs:35–36,667–675,719–721`).

The other three fences that Task 4 preserves remain in the same transaction
(`crates/groupware/src/calendar/itip.rs:1082,1093,1107`). They still reject the stale write
when the first fence is removed. The named test consequently cannot establish the
first-chunk protection that M6 claims to check.

**Correction:** Add `tests/src/za/mail/fence.rs` to Task 4 and enable
`ForceCommitSplit::new(account_id)` around the stale merge and its successful control.
Retain the unchanged-event assertion and verify that M6 then fails there. Removing all
four fences instead would check whole-path refusal, but would leave the per-chunk property
unproven. This finding is established by source inspection; the mutation was not executed.

### R4 — [P2] Include the new runtime helpers in the C10 coverage cohort

**Plan: 313–317 and 367–372.** The plan creates
`crates/email/src/message/za/harvest.rs` and `crates/services/src/state_manager/za.rs`,
but never adds either to `tests/qualification/dispositions.json`'s `cohort.additions`.
The referenced C10 design explicitly includes fork runtime code added during the port
(`docs/superpowers/specs/2026-10-27-stalwart-1-upgrade-design.md:617–625`).

`scripts/tests/check_coverage.py:51–89` enumerates only exact baseline and addition entries;
it does not discover new files under an existing directory. Unlisted crate files go into
the report-only `upstream_product` group (`:180–208`). Thus uncovered new harvest or push
fallback logic contributes to neither coverage gate's denominator or numerator, despite
the plan claiming those gates for the resulting fork.

**Correction:** Assign both runtime additions to a task before Task 9, with
`runtime_excluded: false` and evidence. Classify the standalone codec test file under
`excluded_additions`. The existing release-5 entries at
`tests/qualification/dispositions.json:797–827` show both classifications.

### R5 — [P2] Set the intended fork version before product qualification

**Plan: 526–540, 550 and 595–596.** Task 9 builds and verifies the product, runs its
fresh-store restart check, and dispatches CI. Only afterwards does Task 10 change the
shipping manifest, lock entry and `fork-release.toml` to `0.4.0-beta.1`. Task 10 repeats
Python checks and formatting, but does not build or qualify that resulting binary.

The recorded product is therefore the earlier `0.3.0-beta.1` binary. This matters to the
repository's actual acceptance path: `scripts/release/verify_product.py:64–79` binds the
binary's identity to its version and source SHA, and CI's restart gate consumes the product
whose identity was verified (`.github/workflows/test.yml:443–455,549–562`). Tooling unit
tests alone do not validate the later product.

**Correction:** Move the fork-version changes into Task 2, before the integrated product
gates. Alternatively, explicitly rebuild, verify the identity, and run the restart check
against the product after the release-identity change, recording its actual source SHA.
Prose-only edits do not require repeating the entire functional matrix.

### R6 — [P2] Make combined branch review a completion gate

**Plan: 598.** The hand-off makes a clean-context whole-branch review an optional PR-stage
offer. The supplied AGENTS guidance requires an independent final whole-branch review for
changes spanning critical contracts or interacting components when focused reviews cannot
establish their combined correctness. Here, the account flag and cache changes, harvest
gate, sealed ingest, push conversion, and calendar transaction fences are implemented and
reviewed in separate tasks, while their combined behavior is the purpose of the merge.

The earlier upgrade's execution gate also explicitly required this combined review after
the integrated checks
(`docs/superpowers/specs/2026-10-27-stalwart-1-upgrade-design.md:665–676`). Task-level
reviews and the hook-count census do not provide that final view of the integrated branch.

**Correction:** Add a required fresh, read-only whole-branch review after integration,
with the base/head refs and accepted contracts, and close its findings before declaring
the merge qualified. Keep the separately authorized Fable review and PR creation separate;
this does not require invoking Fable without authorization.

### R7 — [P3] Resolve the lock-check helper from the main checkout

the selected worktree, but that directory does not exist there. The supplied helper lives

The command will fail before checking any lockfile.
