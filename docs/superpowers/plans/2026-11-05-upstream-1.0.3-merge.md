**Goal:** Move the fork's upstream base from Stalwart v1.0.1 to v1.0.3 (which contains v1.0.2), with every zero-access invariant holding on the new base, every existing suite passing, and each new upstream surface that can reach a key account gated, tested or recorded.

**Architecture:** One `git merge --no-ff v1.0.3` on branch `upstream-1.0.3`, committed raw with its 15 conflicts, then resolution tasks in crate dependency order (`store` → `common` → `groupware` → `email`/`smtp`/`imap` → `services` → `jmap` → `http`), each a reviewed commit. Fork code changes only where an invariant needs it: two new fork modules (`crates/email/src/message/za/harvest.rs`, `crates/services/src/state_manager/za.rs`), one-line insertions elsewhere, and test changes. The test crate, the leak checks and the integrated matrix follow, then documentation and release identity.

**Tech Stack:** Rust 2024 on upstream v1.0.3. It adds the `crypto` crate, which replaces `sequoia-openpgp` and the `rasn` stack, and moves `mail-auth` from 0.14 to 0.15.1. It also adds the blob codec (`BlobOpts`, `BlobKeyring`, trailer-encoded compression and AES-256-GCM/ChaCha20-Poly1305 blob encryption). The rest is the fork's existing tooling: RocksDB, the `tests` crate harness, the Python release and gate tools, and GitHub Actions.

## Decisions for Jay (the plan's defaults until Jay answers)

Each line gives the default the plan executes and its source finding.

1. **Fork version.** `0.4.0-beta.1`, set in Task 2 of this branch, so that every product Task 9 qualifies carries it: a base move is a minor bump, the precedent `0.2.0-beta.1` set. Tagging and publishing stay separate. The alternative is `0.3.0-beta.2`. (F7, review R5)
2. **Key harvesting.** A key-account recipient never contributes, per recipient: a plain co-recipient of the same message still harvests. This is upstream's 1.0.2 harvest of sender keys from DMARC-pass mail into plaintext `ExternalPublicKey` rows. It is reachable only when the operator sets `Encryption.gatewayEnable`, but the operator is the adversary.
   - A recipient contributes only when its own delivery committed a message as an ordinary account. The decision is taken after the delivery's outcome, from that outcome and a fail-closed classification read after it, with no lookup before the ingest (review R1, revisions 2 and 3).
   - Why that is safe:
     - an ordinary commit carries the provisioning fence, and once it lands, setup refuses the account (it holds mail, or `setup-token`'s recheck rolls back);
     - a committed write for a key account needs its vault.
   - So the classification read after a committed outcome is the one the ingest used.
   - Every other outcome contributes nothing, for every account:
     - a refused or failed delivery: a pending account without a served key, a lost fence, a quota error;
     - a Sieve outcome that wrote nothing: discard, redirect only, reject;
     - a duplicate.

     For ordinary accounts that is a small departure from upstream, which also harvests from failed deliveries; the retry harvests once it lands.
   - **What the per-recipient rule still exposes (F15).** When a message to a key account also goes to a plain co-recipient whose delivery commits, the harvest runs on the plain recipient's account. It then stores, in the clear, the key account's correspondent: the header From, the key, and first and last seen. It also traces the From and the fingerprint.
     - The plain recipient's mailbox holds the same message in the clear, and the operator can read it there; the decision accepts that.
     - The alternative, suppressing the whole message when any recipient is a key account, closes it.
   - Alternatives: suppress the whole message when any recipient is a key account, or no code gate. (B4, B-J1)
3. **Push for key accounts.** The state change that replaces a key account's EmailPush is delivered whatever the subscription's `types` holds. This mirrors upstream 1.0.3, which delivers an EmailPush regardless of `types`, and keeps both existing tests unchanged. The alternative filters it by `types`, which silences a key account's subscriber whose `types` is `[]`. (C1, C2)
4. **`/jmap/upload` order.** Upstream's `assert_is_member` runs first, then the fork's keyless gate. This closes the key-or-plain classification oracle the fork's 403 gives a non-member; non-members get 400. The alternative keeps the fork gate first and the oracle. (A3, C4)
5. **Upstream per-account encryption at rest on a key account.** Left settable and inert: ingest seals the message as received, and a test pins this. The alternative refuses `Enabled` in `validate_encryption_at_rest` for key accounts. (A11, B5, B17)
6. **Epoch bump in upstream's default-role invalidation.** Adopted: one line, so a loader in flight cannot republish a token with the old role permissions. No zero-access invariant needs it; it makes upstream's 1.0.3 fix race-free under the fork's loader fences. (A12)
7. **The outbound encryption gateway on key accounts' mail, the iMIP submitter included.** Accepted as upstream behaves. `encryption.gateway-encrypted` traces the recipient key's fingerprint, an envelope-class value, recorded beside the queue events' addresses in invariant 47's wording. (B7, B-J2)
8. **iTIP override rule (1.0.3).** A full REQUEST no longer removes an override whose stored SEQUENCE is above the master's. This is accepted as parity: key attendees behave as ordinary ones, and the drain calls upstream's merge. The pinning comment on ruling 132 gains the condition. A fork-only mitigation for key organizers is the alternative. (E6, E-J1)
9. **Stores written by 0.3.0-beta.1.** Recreated under the fresh-store rule, with no carry-over qualification. Schema base stays 7 and no conversion exists, so a carry-over would likely open, but nothing here tests it. Whoever carries one over starts it once with `STALWART_UPDATE_ROLE_PERMISSIONS=true`. (D13, A13, A-D5)

## Review Focus

1. **The key flag lost in `principals.rs`.** A resolution that takes the fork's side inside every conflict block of `crates/common/src/cache/principals.rs` still leaves upstream's auto-merged `flags: ACCOUNT_IS_USER,` (raw-merge line 577), outside the markers. Every key account would then load as ordinary and its mail be stored in the clear; the build only warns about an unused variable (A1, B3). Expected: the loader sets `ACCOUNT_IS_KEY_ACCOUNT`. Pinned by Task 3's `key_flag_survives_the_loader` and Task 9's mutation M1.
2. **The `itip.rs` gates and fences dropped.** Taking upstream's side of the `itip.rs` hunks drops both RSVP key-account gates and all four `commit_itip_merge` fences, and still compiles: upstream moved those functions into trait methods (E1, E2). Expected: 8 fence calls and 2 gate calls in the file. Pinned by Task 4's count check, `gating::test_scheduling`, `mail::fence`'s `forward_race_imip_merge`, and mutations M5 and M6.
3. **Upstream's encryption reaching a key account's mail.** An operator enables `Encryption.gatewayEnable`, or a key account selects `encryptionAtRest: Enabled`. Without the fork's gates, mail delivered to a key account feeds the plaintext harvest (correspondent addresses, keys and sightings, and the From header in traces), or is OpenPGP-encrypted before sealing (B4, B5). The same applies to a delivery that raced setup (R1): one that lost the fence, one refused because setup was pending, or one sealed because setup completed before the ingest read the account. Expected: sealed exactly as received, with no harvest row or From trace from any delivery that did not commit a message as an ordinary account. Pinned by Task 5's `za::mail::gateway` cases and mutations M2, M3 and M3b.
4. **Leak checks blinded by the blob codec.** An operator configures zstd or a `SymmetricKey` for blobs. Leak checks that read raw blob bytes then pass vacuously, or, with an empty keyring, bury the canary search under decode violations (D5, D7). Expected: the scanner decodes through the server's keyring and still finds a planted plaintext. Pinned by Task 8's `leak::test_codec` and mutation M8.
5. **Push.** A key account's message arrives by IMAP APPEND or `Email/import`, which emit EmailPush at 1.0.3, on a subscription whose `types` is `[]` (C1–C3). Expected: a state change only, and delivered. Pinned by Task 6's extended `push_is_state_only` and mutation M4.
